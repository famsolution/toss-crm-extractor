# 금소법/상품비교 확인서 전송 자동화 — 설계 및 검증 결과

작성일: 2026-06-11 · 대상: 토스인슈 CRM `확인서 전송` 플로우 자동화

---

## 1. 한 줄 요약

확인서 전송 플로우의 핵심 단계가 **Flutter(CanvasKit) 캔버스**라 일반 확장(DOM 셀렉터)으로는 자동화가 안 된다. 대신 **백엔드 API로 상품 카탈로그를 받아 제안서 상품명과 fuzzy 매칭**하면, 가장 번거로운 "유사 상품 선택"을 신뢰성 있게 자동화할 수 있다(실측 검증 완료). 입력·클릭 실행은 시각 기반 에이전트(Claude+Chrome)가 담당하는 **하이브리드** 구조가 현실적이다.

---

## 2. 전체 플로우 (실측)

진입: `/crm-v2/center/pcs-documents` (React, 실제 DOM) → 우측 상단 **확인서 전송하기** → 새 탭 `/crm-v2/center/pcs-documents/send` 가 열리고 그 안에 **Flutter iframe** 로딩.

단계 표시(상단 스텝퍼): **기본정보 → 상품비교 → 금소법 → 서명&완료**

| 순서 | 화면 | 동작 | 유형 |
|---|---|---|---|
| 0 | 확인서 종류 선택 | 상품비교 확인서 + 금소법 고지 확인서 (기본 둘 다 체크) → 다음 | Flutter |
| 1 | 기본정보 입력 | 고객명·연락처·증권번호(선택)·생일 입력 → 다음 | Flutter |
| 2 | 상품비교 | 카테고리(장기/일반/자동차) 선택 → **보험사 검색·선택 → 상품명 검색·유사선택** → 다음 | Flutter |
| 3 | 금소법 | (고지 확인 단계) | Flutter |
| 4 | 서명&완료 | 고객에게 URL 발송 → 서명 요청 (**되돌릴 수 없음 — 자동화 금지, 사람이 확인**) | Flutter |

> ⚠️ 서명·전송은 고객에게 법정 확인서가 실제 발송되는 비가역 동작이다. 자동화는 그 **직전까지만** 수행하고 최종 전송은 사람이 누른다.

## 3. 기술적 제약 — 왜 확장만으로는 안 되는가

- `/send` 의 본문은 `crm.tossinsu.com/flutter-app` 을 **CanvasKit 렌더러**로 그린다. DOM 상 `input`/`select`/`button` 이 **0개**, 화면 전체가 `<canvas>` 픽셀.
- Flutter 접근성(Semantics) 트리는 합성 클릭으로 켜지지 않음 → 요소 좌표/라벨을 안정적으로 못 얻음.
- 상품 목록은 앱 메모리(Dart) 안에서 클라이언트 필터링 → 확장이 옵션 텍스트를 **읽을 수 없음**.
- 단, **실제 OS 클릭 + 타이핑은 정상 작동**(검증). 포커스된 칸은 숨겨진 `flt-text-editing-host > input` 으로 입력이 전달됨.

결론: "어떤 상품들이 떠 있는지 읽고 고르는" 판단은 캔버스를 *볼 수 있는* 주체(시각 에이전트)나 *데이터를 직접 받는* 경로(API)만 가능하다.

## 4. 돌파구 — 백엔드 API (동일 출처, 쿠키 인증)

```
GET /api-mobile/v3/crm/pcs/insurance-company/list?name=메리츠
  → { success: { companies: [{ inscoCd:"N16", inscoNm:"메리츠화재" }] } }

GET /api-mobile/v3/crm/pcs/product/by-company?inscoCd=N16
  → { success: { products: [{ procNm, productCd, isForSale, option1Nm, ... }] } }   // 메리츠 2264개
```

`procNm`(정식 상품명)과 `productCd`(상품코드)를 그대로 받으므로, 캔버스를 읽지 않고도 제안서 상품명과 **문자열 매칭**이 가능하다.

---

## 5. 매칭 알고리즘 (검증 완료) — `pcs-product-matcher.js`

1. **정규화**: 한글·숫자만 남기고 공백·괄호·특수문자 제거(+"메리츠" 노이즈 제거). 띄어쓰기/기호 차이를 무력화.
2. **점수** = `0.7 × Dice(문자 bigram) + 0.3 × Jaccard(숫자/버전 토큰)`.
   - 숫자토큰 가중이 `3.10.5 vs 3.0.5`, `세만기형(2604) vs 연만기형` 같은 미세 차이를 가른다.
3. **확신격차** = 1순위 − 2순위 점수. `≥0.05` 면 자동 선택, 낮으면 사람 확인 권장.

실측 (메리츠 2264개, onlyForSale):

| 후보 | procNm | 점수 |
|---|---|---|
| **1순위 ✅** | …2604(통합간편심사형) (3.10.5간편심사형) 해약환급금미지급형 보험료 납입면제2형 `N1611474962798` | 0.808 |
| 2순위 | …2604(**연만기형**) (통합간편심사형) (3.10.5간편심사형)… | 0.756 |
| 3순위 | …2604(통합간편심사형) (**3.0.5**간편심사형)… | 0.721 |

제안서명 `(무) 메리츠 통합간편건강보험(세만기형)2604(통합간편심사형)(3.0) (해약환급금미지급형(납입후50%))(보험료 납입면제 2형)(3.10.5 간편심사형)` → 1순위 정확 매칭, 확신격차 0.052.

## 7. 권장 아키텍처 (하이브리드)

- **확장(content.js)** — React 영역 담당: `/pcs-documents` 진입, 고객 데이터 추출, `확인서 전송하기` 클릭. + **상품 매칭 API 호출**(세션 쿠키 보유)으로 `procNm`/`productCd` 산출. → 결과를 에이전트/UI에 전달.
- **에이전트(Claude+Chrome)** — Flutter 영역 담당: 기본정보 입력 → 카테고리/보험사 선택 → **매칭으로 확정된 정확한 procNm** 으로 상품 검색·클릭 → 금소법 단계 진행 → **서명·전송 직전 정지**.

핵심: 확장이 미리 "정확히 이 상품(procNm/productCd)" 을 알려주므로, 에이전트의 상품 선택에서 모호함이 사라진다.
